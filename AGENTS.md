## 2. Как течёт состояние (цикл)

```
 ДИСК (map.svg + state.json)
   ↑ читает            ↓ пишет (save_project)
 СЕРВЕР (map_server.py → map_catalog.py)
   ↑ отдаёт            ↓ принимает (POST action=save)
 БРАУЗЕР (cartographer.html, живой SVG в памяти)
```

- **Загрузка:** диск → сервер читает файлы → браузер строит карту в памяти.
- **Редактирование:** меняется картинка и журнал **только в памяти браузера**.
- **Автосохранение:** само, ~1.2 с после правки и при закрытии вкладки →
  браузер шлёт `svg`+`state` на сервер → `save_project` пишет на диск.

Зависимости: редактор зависит от сервера; сервер зависит от диска; диск — конечная
истина, **НО** перезаписывается браузером при каждом сохранении. Верификатор ни от
кого не зависит и ни на что не влияет.

## 3. Инцидент #1 — маркеры (фиолетовые) на слое «Волга»

**Симптом:** на карте появляются фиолетовые маркеры (обычно `<path data-kind="marker">`,
заливка `#ff00ff`), часто в слое «Волга» (id слоя 3, становится активным после
перезагрузки). Могут «рендериться каждый раз» даже после очистки файлов.

**Корень проблемы (важно):** маркер попадал **и в `map.svg`, и в журнал `state.json`**
(оверлей `"Маркер 1"`). Возникал замкнутый круг:
> сервер отдал маркер → браузер нарисовал → браузер сохранил обратно → сервер записал
> на диск → снова отдал → …

Поэтому «просто почистить файл на диске» **недостаточно** — старая открытая вкладка
со старым кодом перезаписывала его обратно. Ещё одна ловушка: очистка маркеров только
в оверлее `debug_overlay.js` не работает, если отладочные переключатели выключены
(по умолчанию OFF) — код очистки тогда не запускается.

**Точки исправления (уже применены, НЕ удалять):**
1. `prototype/cartographer.html`:
   - `stripMarkers()` — вырезает `path[data-kind="marker"]` из живого SVG при
     каждой загрузке карты (`remountSvg`) и при каждом восстановлении снимка
     (`restoreSnapshot`). Работает **независимо от отладочных переключателей**.
   - `sanitizePending()` — удаляет оверлеи `"Маркер *"` из загружаемого
     `pendingLayerState`/журнала до применения.
   - `upsertOverlay()` — отказывается создавать путь с `data-kind="marker"`.
   - `currentOverlays()` — отказывается захватывать маркеры, поэтому автосохранение
     не может снова записать их в `state.json` (состояние самоочищается).
   - `applyMarkerStroke()` — заглушка, ничего не создаёт.
2. `scripts/map_catalog.py` (`save_project`):
   - `_strip_markers_from_svg()` — вырезает элементы с `data-kind="marker"` /
     `data-label="Маркер*"` и `fill="#ff00ff"` из SVG **перед записью на диск**.
   - `_strip_markers_from_state()` — удаляет ключи `"Маркер*"` из `state` перед записью.
   Это серверная защита: даже старая вкладка не сможет записать маркер на диск.
3. `*.good` файлы и `map.svg`/`state.json` очищены от маркеров (верификатор зелёный).

## 4. Чеклист перепроверки при рецидиве маркеров

Если маркеры снова появились — пройти по порядку:

1. **Жёсткая перезагрузка редактора** (Ctrl+Shift+R) — старая вкладка держит старый
   JS в памяти и продолжает показывать старые маркеры. Новый код их не создаст.
2. **Проверить диск на маркеры** (см. команды ниже). Если нашлись — почистить и
   убедиться, что сервер живёт с новым `map_catalog.py` (п.3).
3. **Проверить, что сервер перезапущен с новым кодом** — `map_catalog.py` читается
   сервером при старте, поэтому после правки `map_catalog.py` сервер **надо
   перезапустить** (см. команды).
4. **Проверить live-ответ сервера**: запросить `map.svg` и `state.json` через API и
   убедиться, что маркеров в ответе нет.
5. Если маркеры всё ещё в DOM браузера после перезагрузки — искать НОВЫЙ путь
   реинъекции (не `data-kind="marker"` и не `"Маркер"`), вероятно через `overlays`
   или `paths` в `state.json`; расширить `_strip_markers_from_svg/_from_state` и
   `stripMarkers()` под новый паттерн.

## 6. Прочие заметки
- Сплайны (C-кривые) намеренно отключены: `materializeSplines` — no-op,
  `renderDistrictSide` рисует функционально с комментарием `// SPLINE DISABLED`.
  Верификатор (`verify_map_good.py`) ожидает отсутствие C-кривых в `map.svg`.
- При добавлении новых защит/инвариантов — синхронизировать `*.good` эталоны и
  `verify_map_good.py`, иначе верификатор будет ложно падать.
- **Защита от дурака (pre-commit):** хук `hooks/pre-commit` активируется один раз
  на клон — `git config core.hooksPath hooks` (уже сделано в этом рабочем дереве).
  Он блокирует коммит, если в `map.svg`/`map.svg.good` есть маркеры
  (`data-kind="marker"` / `Маркер` / `#ff00ff`) либо `verify_map_good.py` падает,
  и напоминает бампнуть эталон, когда меняется `map.svg` без `map.svg.good`.
  Обойти намеренно: `git commit --no-verify`.
- **Поднять эталон:** `python scripts/bump_good.py` копирует `map.svg`/`state.json`
  в `*.good` и гонит верификатор; изменившиеся `*.good` коммитить отдельно.
- Коммитить только по явной просьбе пользователя. Ветка: `feat/pencil-volume`.
